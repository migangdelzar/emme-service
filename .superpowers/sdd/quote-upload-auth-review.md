## Executive assessment

The patch closes the original unauthenticated quote-upload boundary in the
controller: it adds method security, resolves authorization from the backend
context, performs a tenant-scoped conversation lookup before storage, and keeps
the existing compensation path. The changed files are narrowly scoped and the
focused controller tests pass.

The ownership check is not compatible with the existing conversation identity
model, however. It compares the AI context's hashed issuer/subject identity to a
conversation `participantId`, although the conversation API and WhatsApp flow
currently use channel-participant or caller-supplied participant IDs. This can
deny legitimate quote submissions and means the new “owned” fixture does not
represent a conversation created through the supported API.

## Findings

### F-01 — Medium: ownership key is not the conversation participant key

`DesignQuoteController.authorize` accepts a conversation only when
`context.principalId()` equals `ConversationDetails.participantId()`
(`DesignQuoteController.java:120-127`). `context.principalId()` is generated by
`AiPrincipalIdentity.fromTrustedClaims(issuer, subject)`, a deterministic
PII-free hash of the JWT issuer and subject.

The existing conversation model does not establish that invariant:

- `StartConversationRequest` accepts an arbitrary `participantId` and
  `AssistantWebMapper` passes it directly into `StartConversationCommand`.
- `StartConversationService` persists that value unchanged.
- `ProcessWhatsAppMessageService` creates conversations with
  `ChannelParticipant.id()`, while its AI context principal is based on the
  customer ID or provider reference, not that channel-participant ID.

Therefore a normal conversation created by the current web API or WhatsApp
flow will generally not match the hashed JWT principal. The endpoint will
return `AccessDeniedException` before storage even for the legitimate owner.
The positive unit fixtures avoid this by constructing `ConversationDetails`
with the hashed JWT principal directly; they do not exercise a conversation
created through the supported application boundary.

This is a security/compatibility correctness issue: the check fails closed, but
it does not enforce ownership according to the system's existing identity
contract and can make the quote capability unusable.

**Required direction:** define and use one canonical ownership relation. For
example, derive the web conversation participant from the authenticated
principal and migrate the conversation API away from caller-supplied identity,
or resolve the authenticated customer/channel participant and compare that
canonical ID instead. Then add an integration test that creates a conversation
through the supported API and successfully uploads as its owner, plus
same-tenant cross-principal and cross-tenant denial cases.

### F-02 — Low: the real method-security boundary is not tested

The added tests invoke `DesignQuoteController.submit` directly, so Spring's
`@PreAuthorize` expression is never evaluated. The role and feature assertions
exercise only the duplicated `authorize` method through a test-supplied
`AiAuthorizationContextResolver`. There is no HTTP/proxy test proving that:

- a non-client authority is rejected by the annotation;
- `ai_chat` is evaluated through the tenant-aware `featureFlagService`; and
- the multipart endpoint cannot reach the method before authorization fails.

The existing `SecurityConfiguration` has `@EnableMethodSecurity`, and the
expression is consistent with other controllers, so this is a coverage gap,
not evidence that the annotation is currently broken. Add one `MockMvc` test
with the quote feature enabled and client/tenant contexts, alongside the
denied-role and disabled-feature cases.

## Positive observations

- Tenant identity is taken from `TenantContextHolder` through
  `AiWebExecutionContextFactory`; the request does not supply a tenant ID.
- The conversation lookup is issued with
  `new GetConversationQuery(context.tenantId(), conversationId)`, and the
  application adapter uses `findByIdAndTenantId`, preventing a cross-tenant
  conversation from being returned by the normal persistence path.
- The controller rechecks tenant equality and principal equality before any
  image bytes are read into storage, metadata is saved, or quote workflow
  execution begins.
- Role and capability checks fail closed. The endpoint requires a client role,
  the `ai_chat` feature, and the `ai:basic` tenant capability.
- The new dependency is injected through `GetConversationUseCase`; all
  in-repository constructor call sites were updated, and no unrelated
  production files were changed. The constructor source compatibility change
  is therefore appropriate for this internal controller boundary.
- Existing image validation and cleanup behavior remains in place, including
  cleanup of stored bytes when a later multipart read or workflow step fails.
